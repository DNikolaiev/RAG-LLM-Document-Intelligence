# Policy-lab upload runbook

This runbook drives the whole policy pipeline by hand: policy upload, clause extraction, rule
proposal and its blocking gates, the field-proposal and dedup path, and fact extraction against a
live rule.

It uses the 13 PDFs in [`fixtures/documents/policy-lab/`](../../fixtures/documents/policy-lab),
generated by [`scripts/generate-policy-lab-fixtures.py`](../../scripts/generate-policy-lab-fixtures.py)
and verified by `python scripts/verify-fixtures.py`. Every organisation, person, reference, and
value in them is invented. Nothing here is seeded for you: each step is a manual upload.

The pharmacy workspace (Düsseldorf Health Operations) is out of scope. Only the three
single-document-type workspaces are used.

## Before you start

1. Start the local production profile:

   ```bash
   docker compose -f infra/docker-compose.production-local.yml \
     --env-file infra/.env.production-local up --build -d
   ```

2. Open the review console at <http://127.0.0.1:3000>. The API is at <http://127.0.0.1:4100>.
3. The policy library is at <http://127.0.0.1:3000/policies>.
4. Use the profile switcher in the header to become the administrator of the workspace you are
   working in. Each profile administers exactly one workspace:

   | Workspace                | Tenant id              | Profile to select | API header value       |
   | ------------------------ | ---------------------- | ----------------- | ---------------------- |
   | Rheinland Legal Services | `tenant_legal`         | Jonas Feld        | `profile_jonas_feld`   |
   | Helios Claims Europe     | `tenant_insurance`     | Amara Okafor      | `profile_amara_okafor` |
   | RuhrWorks Manufacturing  | `tenant_manufacturing` | Mateo Klein       | `profile_mateo_klein`  |

Policy processing runs on a real model through the worker queue. Expect roughly one to a few
minutes per policy on CPU-only local models. The bell icon in the header shows the processing
timeline for the upload you just made.

## The five outcomes this pack produces

| Outcome | What it is                                 | Where you see it                                                                                          |
| ------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| A       | An approvable rule                         | Policy detail page: a proposal with passing rule tests and an **Approve proposal** button                 |
| B       | Rule blocked `condition_too_weak`          | Policy detail page: proposal marked `invalid`, only a **Dismiss blocked rule** button                     |
| C       | Rule blocked `citation_condition_mismatch` | Same place, different stated reason                                                                       |
| D       | A new field proposal                       | Policy library → **Fact vocabulary** → **Show fields** → **Field proposals**                              |
| E       | An alias proposal (dedup merge)            | Same panel, card headed "New wording for …" with a **Merges into …** note and an **Approve merge** button |

An outcome-A policy is the only one you activate; the others are meant to be blocked, and blocked
proposals cannot be approved at all.

## How to upload one policy

1. Switch to the workspace profile from the table above.
2. Go to <http://127.0.0.1:3000/policies>.
3. In **Add policy version**, fill in:
   - **Workspace** — the workspace named in the file's row below.
   - **Policy title** — the suggested title in the file's row below.
   - **Version** — `1.0` (use `1.1`, `1.2`, … if you re-upload the same title).
   - **Collection** — the collection named in the file's row below.
   - **Valid from** — leave today's date.
   - **Language** — `English`.
   - **Original PDF** — the file from `fixtures/documents/policy-lab/…`.
4. Press **Upload and process**, then wait until the policy appears in the version list with status
   `under review`.
5. Open the policy from the list to read its proposals, citations, and rule tests.
6. Field proposals do **not** appear on the policy page. They are in the policy library under
   **Fact vocabulary** → **Show fields** → **Field proposals**, scoped to the selected workspace.

## Rheinland Legal Services — `tenant_legal`

Collection for both policies: **Commercial contract policy** (`commercial-contract-review-policy`).

### Policy 1 — outcome A, an approvable rule

- File: `fixtures/documents/policy-lab/legal/01_termination-notice-minimum-policy.pdf`
- Suggested title: `Termination Notice Minimum Control`
- Load-bearing clause:
  > The termination notice period agreed in a commercial contract must be at least ninety (90) days.
- Why it is approvable: the clause names `notice period`, which is an alias of the existing field
  `contract.terminationNoticeDays`, and it states a number, so the rule can be written as a numeric
  comparison rather than a presence check.
- Expect: one proposal that flags a notice period shorter than 90 days, with four passing rule
  tests and an **Approve proposal** button.
- Do this: press **Approve proposal**, then **Activate policy and approved rules**. The rule then
  shows in the library's **Rule registry** tagged `FROM POLICY REGISTER`.

### Policy 2 — outcome C, blocked as `citation_condition_mismatch`

- File: `fixtures/documents/policy-lab/legal/02_jurisdiction-escalation-policy.pdf`
- Suggested title: `Jurisdiction Escalation Control`
- Load-bearing clause:
  > A commercial agreement must be escalated when it is subject to courts outside Germany.
- Why it is blocked: the only field this condition can target is `contract.governingLaw`, and the
  clause names neither its label (`Governing law`) nor its alias (`applicable law`). Nothing
  anywhere in this PDF names a catalog field, so whichever clause the model cites, the citation
  cannot ground the condition.
- Expect: a proposal marked `invalid` whose stated reason is that the cited clause does not name
  Governing law. There is no **Approve proposal** button, only **Dismiss blocked rule**.
- Do this: read the reason, then dismiss it. Do not activate this policy.

- File: `fixtures/documents/policy-lab/manufacturing/02_heat-number-cross-check-policy.pdf`
- Suggested title: `Heat Number Cross-Check Control`
- Load-bearing clause:
  > The heat number stated on the material certificate must match the heat number recorded on the
  > mill test report issued by the steel producer.
- Why it is blocked: the clause does name `heat number`, so the citation grounds correctly, but it
  demands a match against a mill test report the pack holds no fact for. The only condition that
  could be written is a presence check on `material.heatNumber`, and a presence-only condition is
  not allowed to stand for a clause that demands a comparison.
- Expect: a proposal marked `invalid`, with a reason saying that the cited clause requires a
  comparison, date, or matching check and that a presence-only condition is not sufficient.
- Do this: read the reason, then **Dismiss blocked rule**. Do not activate this policy.

## Running a case

The console has no run button, so create the case, attach one evidence PDF, and start processing
through the API. Run these from the repository root.

```bash
API=http://127.0.0.1:4100
PROFILE=profile_jonas_feld          # or profile_amara_okafor / profile_mateo_klein
PACK=pack_tenant_legal              # or pack_tenant_insurance / pack_tenant_manufacturing
FILE=fixtures/documents/policy-lab/legal/03_talwerk_supply_agreement_extract.pdf
LABEL=legal-satisfies               # any short unique label for this case

# 1. Create an empty case and note the id it returns.
curl -s -X POST "$API/v1/cases" \
  -H "x-test-profile-id: $PROFILE" \
  -H 'content-type: application/json' \
  -H "idempotency-key: policy-lab-$LABEL" \
  -d "{\"subjectName\":\"Policy lab $LABEL\",\"domainPackId\":\"$PACK\",\"reference\":\"LAB-$LABEL\"}"

CASE=case_...                       # paste the id from the response

# 2. Attach exactly one evidence PDF.
curl -s -X POST "$API/v1/cases/$CASE/documents" \
  -H "x-test-profile-id: $PROFILE" \
  -F "file=@$FILE;type=application/pdf"

# 3. Start processing.
curl -s -X POST "$API/v1/cases/$CASE/process" \
  -H "x-test-profile-id: $PROFILE" \
  -H "idempotency-key: policy-lab-$LABEL-run"
```

Then open `http://127.0.0.1:3000/cases/$CASE` with the same profile selected in the switcher and
read the review panel: the extracted facts on the left, the findings on the right.

Rules of thumb:

- One evidence PDF per case. Facts merge across every document in a case, so a satisfying and a
  violating document in the same case give an ambiguous result.
- Activate the policy **before** you run the case. Only rules that are active when the case runs
  are evaluated.
- Re-running the same `idempotency-key` returns the same case or job instead of creating another.
- To re-run a case against a widened pack after approving a field proposal, use
  `POST /v1/cases/$CASE/reprocess` instead of `process`.

## If something does not match

The blocking gates (C and B) and the field-grounding checks are deterministic: they compare the
model's citation against the field labels and aliases in the pack, so a proposal built on these
clauses can only be blocked. What is **not** deterministic is whether the model proposes a rule or
field at all, and how it words a label. Treat these as the acceptance conditions:

- Outcome A passes if a proposal is approvable and its rule tests pass. The exact title, severity,
  and threshold wording are the model's.
- Outcome B passes if the proposal is `invalid` for a presence-only condition.
- Outcome C passes if the proposal is `invalid` because the cited clause does not name the field.
- Outcome D passes if a field proposal appears with no **Merges into …** note. The proposed path
  and label are the model's; only the meaning has to be tensile strength.
- Outcome E passes if a field proposal appears **with** a **Merges into `claim.estimatedCostEur`**
  note and the approved-field list does not gain a fourth claim field.

If a policy produces no proposal at all, re-upload it as a new version (`1.1`) rather than editing
the PDF; the model is asked again from scratch. If a proposal appears with a different blocking
reason than the one named above, the clause still did its job as long as the proposal is blocked.
