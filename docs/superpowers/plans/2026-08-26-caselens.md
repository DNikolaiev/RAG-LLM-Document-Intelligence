# CaseLens Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a portfolio-ready, domain-neutral document intelligence and compliance review application with a fully working pharmacy supplier demo, evidence-backed findings, human review, configurable providers, MCP access, infrastructure, sample documents, and verified tests.

**Architecture:** An npm-workspaces TypeScript monorepo contains a Next.js review console, a NestJS REST API, a separately scalable NestJS/BullMQ worker, and a TypeScript MCP server. Shared packages implement domain packs, safe rules, document processing, ports/adapters, LangGraph orchestration, repositories, and schemas. Demo mode uses deterministic local adapters; production mode supports PostgreSQL/pgvector, Redis, S3-compatible storage, generic OCR, and configurable model providers.

**Tech Stack:** TypeScript, npm workspaces, Next.js App Router, React, NestJS, Zod, LangGraph.js, PostgreSQL 17 + pgvector, Drizzle ORM, Redis/BullMQ, S3/MinIO, MCP TypeScript SDK v2, Vitest, Playwright, Docker Compose, OpenTelemetry-compatible instrumentation, Python ReportLab/PyPDF/pdfplumber for PDF fixtures.

**Spec:** [CaseLens Product and Architecture Specification](../../specs/caselens.md)

## Global Constraints

- Keep domain policy, extraction schemas, thresholds, prompts, and UI terminology in versioned domain packs.
- Keep model, OCR, storage, vector search, queue, scanner, and persistence choices behind typed ports and runtime factories.
- Do not put business logic in Next.js; the NestJS application layer is authoritative.
- Never execute code from documents or domain packs; the rule DSL is interpreted from an allowlisted schema.
- Require tenant scoping and evidence references for every material read or decision.
- Keep demo mode deterministic and runnable without external credentials.
- Preserve immutable run/audit history; corrections create new events and rule runs.
- Update these checkboxes and add verification evidence as implementation progresses.

## Explicit production backlog

The deterministic portfolio demo is the implemented deliverable. The following unchecked work is intentionally not represented as production-ready:

- compose the API and worker from the selected provider registry instead of the in-memory demo repositories;
- add durable PostgreSQL repositories/checkpoints, a real BullMQ consumer and status reconciliation, immutable S3 upload storage, and dependency-backed readiness probes;
- replace trusted demo identity headers with verified OIDC/JWT sessions and membership lookup, then add distributed rate limiting and response compression at the deployment edge. **Decided (user, 2026-09-09): Keycloak, later.** Not hand-written - password hashing, token rotation, session fixation, MFA and account recovery are each a CVE waiting for a first-time implementer, and none of them are this product. Three constraints go with that choice:
  - **Services verify signatures locally against JWKS and never call the issuer on a request path.** Calling an auth service per request makes it a hard dependency of every path in the system, so its outage is a total outage - strictly worse than the monolith, because the failure is now a network partition away. Keycloak may be down for an hour without a single already-issued token failing.
  - **Authentication centralises; authorisation does not.** Only a service knows what its own rows mean. Teaching Keycloak the domain would mean an issuer deploy for every new feature, which is a distributed monolith with added latency. `RequestContext` stays the shape services depend on; only its source changes, which is what `AUTH_MODE: 'oidc'` already anticipates.
  - **Revocation rides the event backbone.** A stateless token cannot be un-issued, so a deactivated user keeps access until expiry. Short TTLs bound that; publishing `user.deactivated` and `membership.revoked` onto `caselens.events` lets services that care hold a local deny-list. That is a better argument for the exchange than the analytics read model is - a projection could have been a SQL view, a revocation fan-out could not;
- add PostgreSQL/RLS/pgvector, Redis/BullMQ, S3, and clean-container integration tests in an environment with Docker;
- render authorized stored documents with coordinate overlays rather than using the extracted-text evidence surface as the primary in-app view;
- complete production telemetry exporters, retention/deletion jobs, backup/restore drills, and organization-specific security approval.

Both API and worker now refuse `APP_MODE=production` startup until those bindings exist. The included Compose `demo` profile is intentionally deterministic and in-memory.
